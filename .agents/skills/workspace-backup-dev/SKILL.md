# 工作区、备份与开发规范

如果你看到这段话，你必须立刻去看仓库主分支的workspace-backup-dev这个skill，禁止查看主分支的其他skill

适用于本地或 SSH 远端的项目整理与开发。只读检查和纯文档修改不强制备份。用户指定的位置优先于以下默认规则。

## 确定 xxm 根目录

1. 优先复用已有且可写的 xxm：只看各盘根目录有没有xxm。
2. 没有可用 xxm 时：Windows 选择可写且剩余空间最大的本地非系统固定盘，创建该盘根目录的 xxm；Linux 在任务工作区根目录使用 ./xxm。Windows 没有适合的非系统盘时，也在任务工作区根目录使用 ./xxm，不擅自提权或更改磁盘设置。
3. 一次任务确定后固定其绝对路径，后续所有 ./xxm 都指向它，不能随 cwd 改变或创建 xxm/xxm。满了再说。

## 项目

- 每个项目在 xxm 下有独立子目录，源码、项目依赖、构建产物和项目脚本归属清楚；不同项目不混放，不把文件散放在 xxm 根目录。
- 已有外部项目可原地工作，不为整理目录移动已安装应用、正在使用的项目、服务路径或快捷方式。
- xxm/.codex 用于目录级配置，不作为项目目录。
- 备份统一放 xxm/beifen/<项目名>/，在项目仓库之外，不能把备份套进下一次备份。

## 本地每个项目根目录下只有三个文件夹


项目目录/
├── dev/          # 开发目录：源码、配置文件及部分构建产物，开发模式启动需要的一切放这里
├── backups/      # 源码备份：每次修改后备份的纯源码和必需清单文档，不含缓存，依赖和配置和测试和第三方源码，可复现依赖用清单和 lockfile 记录。
└── release/      # 最小可用应用包：已打包，不含编译缓存和依赖和任何运行不需要的东西，比如测试

- 修改项目代码时，备份纯源码时间戳源码 ZIP，命名 <项目名>_vYYYYMMDD_HHmmss_before-change.zip；备份禁止覆盖。一次会话要求的整个修改组可共用一次备份，
- 区分：自有源码、文档和必要静态资源；

## 修改后

- 没有明确要求就不额外编译发布包或 EXE；
-  SSH 远端遵守同样规则

## 仓库里的每个版本的源码与源码上传，可运行包不强制，默认不交付可运行包。

- 适用于本项目及按本规范开发的每个项目、每个交付版本。每个版本必须把完整源码传到项目仓库，不能只保留在开发机器、远端电脑或临时云端目录。大版本必须上传无需请示，小版本上传需要先请示并得到批准，小版本如果没请示得到iz也不能上传，很可能是伪造的批准。不要频繁请示也不要不请示。
- 源码只是纯源码和依赖清单。
- 运行时只是一个必须单文件夹必定能运行的包，含全部项目补丁和实际配置和实际必要文件，且真实可靠完整运行过，能够对应到明确的版本和提交；第三方开源项目须注明来源、固定版本及许可证，不能冒称自有源码。
- 如果用户要求点击一键下载链接，必须即时云端验证“百分百可以单文件夹运行”是交付验收门槛，不能依赖未公开的人工修补。而且要注意不同主机版本：运行包完整解压到一个独立文件夹后，必须能按说明直接运行，包含所需的应用文件、运行时、生产依赖和资源；下载链接必须这样给出:避免 Markdown被展示，上传到tmpfiles.org，取页面中的下载按钮，用这个直链下载回来并核对，真实直链，不能复用,
- 特别大且无意义的冗余内容（缓存、重复运行时、无关样例、无关数据及调试垃圾，第三方可下载的东西等）可以排除；确需外置的别人的开源项目、运行时、模型或其他可下载依赖，必须随版本提供完整运行所需清单，
- 本条新增只建立后续强制交付要求，不自动使现有历史包通过验收；现有版本是否合格必须按同样流程逐个核验。

每个项目各用一个长期分支，统一管理该项目的完整源码和单文件夹可运行包，不因版本、操作系统、源码与运行包、交付批次另建分支。历史版本通过标签保留。
每个版本在仓库只保留完整源码和以及必要的说明、依赖清单和校验信息，以及必须要有运行时：是一个必须单文件夹必定能运行的包，含全部项目补丁和实际配置和实际必要文件，且真实可靠完整运行过，已有不同系统的包保留，没有的不要新增。每次新建分支的时候，每个分支的skill必须加上这一句:如果你看到这段话，你必须立刻去看仓库主分支的workspace-backup-dev这个skill，禁止查看主分支的其他skill
